## Observations

**t+0 — false alarm, mine.** The actuation check flagged "motor not running" at
t=103 s. The profile schedules **0 rpm until t=120 s**; the check did not allow for a
legitimately zero target. Corrected before arming — the alarm now requires
`rpm_target > 0`. Worth remembering: a monitor that cries wolf gets ignored, which
costs more than having no monitor.

**t+2 min — actuation confirmed.** `rpm_target=100`, drive at 1.68 Hz (100/59.5 ✓),
`vfd_is_running=True`, `omron_pv_c=46 °C`. RS485 healthy — the failure mode from this
morning (API holding `/dev/ttyUSB0`, run silently stationary) did **not** recur, even
though the run was started from the UI after a backend restart, which is exactly the
sequence that triggered it.

**t+8 min — tacho artifact reconfirmed.** `rpm_meas=679.23` against a true 100 rpm:
**+579 rpm**, matching the +582 rpm constant offset characterised in ticket 0002.

**t+4 h — first skipped sweep, and the first production proof of a same-day fix.**
Sweep 1013 was lost after three failed attempts. The log shows *why*, which it could not
have done yesterday:

```
[scope_channels] Error applying SP: ConnectionRefusedError(111, 'Connection refused')
[scope_acq] Error applying acquisition settings: ConnectionRefusedError(111, ...)
[sweep 1013/3965] capture attempt 3 failed: Empty PRE? for CHAN1
[sweep 1013/3965] SKIPPED (capture failed); continuing run
```

Those first two lines were `if DEBUG:`-gated and never reached the event log before commit
`5e532382`. The lenient mid-run re-apply also did its job: one sweep lost, not the night.

**Throughout — tacho offset reproducible.** Median offset over 1350 motor-running samples:
**+582.3 rpm**, identical to the previous 13 h run. Excursions cluster at ±100 rpm (one
staircase step) because the tacho lags one telemetry tick across a speed change. Split into
a ~234 rpm baseline with the drive off and a further ~348 rpm that appears only with the VFD
running — reported to ticket 0003 via the bus as an argument for EMI over optics.
